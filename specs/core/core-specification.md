## 2. 目的・適用範囲

Core Specificationは、全コンポーネント・パターン・Reference Implementationに共通する横断的な要求を定義する文書です。
要求は後続Issueで段階的に追加し、小さな単位でレビューできるようにします。
Version 0.1.0では文書管理情報と章構成を整備し、Web標準を基盤とする要求JAUI-WEB-001、意味・セマンティクスを優先する要求JAUI-WEB-002、Web標準の振る舞い・インターフェースを尊重する要求JAUI-WEB-003、アクセシビリティを設計要件として扱う要求JAUI-A11Y-001、標準的なアクセシビリティ基準を参照する要求JAUI-A11Y-002、UIの意味・状態を支援技術へ公開する要求JAUI-A11Y-003、キーボード操作可能性を確保する要求JAUI-A11Y-004、フォーカス順序と管理を適切に行う要求JAUI-A11Y-005、フォーカスの可視性を確保する要求JAUI-A11Y-006、状態変化・フィードバックを適切に伝達する要求JAUI-A11Y-007、エラーの特定・説明・修正を支援する要求JAUI-A11Y-008、色だけに依存せず情報を伝達する要求JAUI-A11Y-009、テキスト・UIのコントラストを確保する要求JAUI-A11Y-010、ターゲットサイズ・間隔を確保する要求JAUI-A11Y-011、動き・アニメーションへの配慮に関する要求JAUI-A11Y-012、入力前のラベル・指示を提供する要求JAUI-A11Y-013、表示条件の変更に対する耐性を確保する要求JAUI-A11Y-014、ポインター操作の代替・取消可能性を確保する要求JAUI-A11Y-015、操作の予測可能性を確保する要求JAUI-A11Y-016を定義します。

アクセシビリティの目標、適合表明の範囲と段階、利用先との責務境界は[14章 Conformance](#14-conformance)で定義します。
本仕様の要求定義は、Componentの実装、実行時検証、Webページ・完全なプロセスのWCAG適合確認の完了を意味しません。

本仕様は、最上位の判断基準である[JaUI Design Principles v0.1](./design-principles.md)の直下に位置します。
Design Principlesに基づいて共通要求を定義し、原則の内容を重複して再定義しません。
個別コンポーネント仕様やLit固有の実装仕様は、本仕様の対象に含めません。

仕様体系は以下の順序を基本とします。

```text
JaUI Design Principles
        ↓
JaUI Core Specification
        ↓
Component / Pattern Specification
        ↓
Decision Records
        ↓
Reference Implementation
        ↓
Test Specification / Results
```

## 3. Web Standards

### JAUI-WEB-001: Web標準を基盤とする

本要求は、[JaUI Design Principles v0.1](./design-principles.md)の原則1「Web標準を置き換えない。拡張する。」を具体化する共通要求です。
Component / Pattern SpecificationおよびReference Implementationから、要求ID `JAUI-WEB-001` で参照できます。

JaUIの仕様およびReference Implementationは、Web標準が提供する既存の意味、振る舞い、機能を基盤として使用しなければならない。

同等の目的を満たすWeb標準の仕組みが存在する場合、合理的な理由なく独自の仕組みで置き換えてはならない。

独自の抽象化または実装を採用する場合、その必要性を説明可能でなければならない。
JaUIによる抽象化または拡張は、基盤となるWeb標準との関係を説明可能でなければならない。

#### 検証可能性

下位仕様またはReference Implementationのレビューでは、少なくとも以下を確認できることを目指します。

- 対象となる標準HTML要素やWeb Platformの機能が存在するか検討されている。
- 独自の抽象化・実装を採用する場合、その必要性を説明できる。
- 基盤となるWeb標準との関係を説明でき、その意味や期待される振る舞いを不必要に失っていない。

ここではレビュー時の確認観点のみを示し、具体的なテスト方法や適合判定手順は定義しません。

### JAUI-WEB-002: 意味・セマンティクスを優先する

本要求は、[JaUI Design Principles v0.1](./design-principles.md)の原則7「見た目より意味・セマンティクスを優先する。」を具体化する共通要求です。
Component / Pattern SpecificationおよびReference Implementationから、要求ID `JAUI-WEB-002` で参照できます。

JAUI-WEB-001がWeb標準を基盤として使用することと独自実装の必要性の説明を扱うのに対し、本要求はUIの目的・役割・期待される振る舞いに対応するセマンティクスの選択を扱います。

JaUIの仕様およびReference Implementationは、UIの視覚表現ではなく、その目的、役割、期待される振る舞いに基づいて、適切なWeb標準の意味・セマンティクスを選択しなければならない。

スタイルまたは視覚上の類似性のみを理由として、本来の目的と異なる意味を持つHTML要素またはWeb Platformの仕組みを使用してはならない。

JaUIによる抽象化またはスタイリングは、基盤となるWeb標準の意味を不必要に変更または曖昧にしてはならない。

#### 検証可能性

下位仕様またはReference Implementationのレビューでは、少なくとも以下を確認できることを目指します。

- UIの目的・役割・期待される振る舞いが明確になっている。
- 採用する標準HTML要素やWeb Platformの仕組みが、その意味に基づいて選択されている。
- 視覚表現やスタイル上の都合だけで、本来の目的と異なるセマンティクスを採用していない。
- JaUIの抽象化やスタイリングによって、基盤となる意味が不必要に失われたり曖昧になったりしていない。

ここではレビュー時の確認観点のみを示し、具体的なテスト方法や適合判定手順は定義しません。

### JAUI-WEB-003: Web標準の振る舞い・インターフェースを尊重する

本要求は、[JaUI Design Principles v0.1](./design-principles.md)の原則1「Web標準を置き換えない。拡張する。」を具体化する共通要求です。
Component / Pattern SpecificationおよびReference Implementationから、要求ID `JAUI-WEB-003` で参照できます。

JAUI-WEB-001はWeb標準を基盤として使用することと独自実装の必要性の説明を扱い、JAUI-WEB-002はUIの目的・役割・期待される振る舞いに対応するセマンティクスの選択を扱います。
本要求は、これらに基づいて適切なWeb標準を選択した後に、その標準が提供する既存の状態・操作・イベント等の契約を維持することを扱います。
[JAUI-A11Y-016](#jaui-a11y-016-操作の予測可能性を確保する)はフォーカス取得・設定変更による文脈変化と文字キーショートカットの条件を扱い、標準契約の維持と併せて適用します。

JaUIの仕様およびReference Implementationは、基盤となるWeb標準が提供する既存の状態、操作、イベントその他のインターフェースを尊重しなければならない。

同等の目的を満たすWeb標準の振る舞いまたはインターフェースが存在する場合、合理的な理由なく、それと矛盾する独自のモデルへ置き換えてはならない。

JaUIによる抽象化または拡張は、基盤となるWeb標準から利用者が合理的に期待する振る舞いを不必要に変更してはならない。

#### 検証可能性

下位仕様またはReference Implementationのレビューでは、少なくとも以下を確認できることを目指します。

- 基盤となるWeb標準が提供する状態・操作・イベント等が確認されている。
- 既存のWeb標準で表現可能なものに対して、不要な独自モデルを導入していない。
- 独自の抽象化・拡張を採用する場合、標準の仕組みをそのまま利用できない理由を説明できる。
- 抽象化・拡張によって、基盤となるWeb標準から期待される振る舞いが不必要に失われたり変更されたりしていない。

ここではレビュー時の確認観点のみを示し、具体的なテスト方法や適合判定手順は定義しません。

本章のその他の要求・詳細は後続Issueで定義します。

## 4. Accessibility

### JAUI-A11Y-001: アクセシビリティを設計要件として扱う

本要求は、[JaUI Design Principles v0.1](./design-principles.md)の原則2「アクセシビリティを後付けしない。」を具体化する共通要求です。
Component / Pattern SpecificationおよびReference Implementationから、要求ID `JAUI-A11Y-001` で参照できます。

JAUI-WEB-001〜JAUI-WEB-003がWeb標準の利用、セマンティクスの選択、標準の振る舞い・インターフェースの尊重を扱うのに対し、本要求はアクセシビリティを設計段階から要求として扱い、下位仕様で明示することを扱います。

JaUIのComponent / Pattern SpecificationおよびReference Implementationは、アクセシビリティを実装後に追加する対応として扱わず、設計段階から要求として考慮しなければならない。

ComponentまたはPatternの意味、情報構造、状態、操作、視覚表現その他の利用方法を定義する際は、それらがアクセシビリティに与える影響を考慮しなければならない。

アクセシビリティ上の要求は、可能な範囲で下位仕様から確認・検証できる形で明示しなければならない。

#### 検証可能性

下位仕様またはReference Implementationのレビューでは、少なくとも以下を確認できることを目指します。

- アクセシビリティが実装完了後の追加対応としてのみ扱われていない。
- 意味・情報構造・状態・操作・視覚表現を定義する段階で、アクセシビリティへの影響が検討されている。
- 下位仕様に必要なアクセシビリティ要求が、確認・検証可能な形で明示されている。
- 視覚上または実装上の都合だけを理由に、必要なアクセシビリティ要求が後回しにされていない。

ここではレビュー時の確認観点のみを示し、具体的なテスト方法や適合判定手順は定義しません。

### JAUI-A11Y-002: 標準的なアクセシビリティ基準を参照する

本要求は、[JaUI Design Principles v0.1](./design-principles.md)の原則2「アクセシビリティを後付けしない。」、原則3「「適合」より「検証可能性」を重視する。」、原則6「DADSを尊重するが、コピーにはしない。」を具体化する共通要求です。
Component / Pattern SpecificationおよびReference Implementationから、要求ID `JAUI-A11Y-002` で参照できます。

JAUI-A11Y-001がアクセシビリティを設計段階から扱い、下位仕様で明示することを扱うのに対し、本要求はアクセシビリティ要求の根拠となる外部基準、その具体化、およびJaUIの責務範囲を扱います。

JaUIのアクセシビリティ要求は、対象となる機能・利用方法に関連する標準的なアクセシビリティ仕様・ガイダンスを参照して定義しなければならない。

参照する外部基準は、JaUIの責務範囲とComponent / Patternの特性に応じて適用し、外部基準の要求をそのまま複製するのではなく、JaUIとして確認・検証可能な要求へ具体化しなければならない。

JaUIは、Component / PatternおよびReference Implementationとして提供・検証できる範囲を明確にし、利用先のWebコンテンツ全体に関するアクセシビリティ適合を、JaUI単体の利用だけを理由として保証してはならない。

#### 参照対象と責務範囲

主要な参照対象として、以下の標準・ガイダンスを対象となる機能・利用方法に応じて扱います。

- [W3C Web Content Accessibility Guidelines (WCAG) 2.2](https://www.w3.org/TR/2024/REC-WCAG22-20241212/)：Level AおよびAAの達成基準を目標とし、適合要件と区別して扱う。参照版・適合表明の方針は[14章 Conformance](#14-conformance)に従う。
- [WAI-ARIA](https://www.w3.org/TR/wai-aria/)
- [WAI-ARIA Authoring Practices Guide (APG)](https://www.w3.org/WAI/ARIA/apg/)
- [HTML Standard](https://html.spec.whatwg.org/multipage/)および関連するWeb Platform仕様
- [デジタル庁デザインシステム（DADS）のアクセシビリティガイダンス](https://design.digital.go.jp/dads/guidance/accessibility/)
- その他、個別の要求に必要な標準・ガイダンス

参照時は、標準の要求とガイダンスの助言・例示を区別します。WCAGの達成基準・規範的定義・適合要件と、Understanding WCAG、APG、DADSの解説・助言・例示を区別し、ガイダンスで規範本文の条件・例外を置き換えません。
この一覧は、各文書の全要求を一括して取り込むことや、外部基準をJaUIの上位仕様として採用することを意味しません。
後続Requirementおよび個別Component / Pattern Specificationで、必要な項目を選択し、JaUIの要求として具体化します。

JaUI側では、提供する機能とその利用条件のもとで確認・検証できる事項を明確にします。
利用者側では、利用先固有のコンテンツ、Component / Patternの組み合わせ、およびページ全体の利用状況を踏まえた確認が必要です。
[WCAG 2.2の適合要件](https://www.w3.org/TR/2024/REC-WCAG22-20241212/#conformance-reqs)が定めるページ全体や完全なプロセスの適合と、JaUIの提供範囲での検証は区別します。

WCAGの参照版・目標レベル、適用判定と適合表明の全体方針は[14章 Conformance](#14-conformance)で定義します。
個別の達成基準との対応やARIA・キーボード・フォーカス等の契約は、既存の個別要求とComponent / Pattern Specificationで具体化します。共通の追跡・評価規則は[13章 Testing](#13-testing)、個別の試験方法・手順・記録書式は下位のTest Specification / Resultsで定義します。

#### 検証可能性

下位仕様またはReference Implementationのレビューでは、少なくとも以下を確認できることを目指します。

- アクセシビリティ要求の根拠となる標準・ガイダンスを説明できる。
- 外部基準を単に引用するだけでなく、JaUIとして確認・検証可能な要求へ具体化されている。
- Component / Pattern単体で確認できる事項と、利用先コンテンツ全体で確認すべき事項が区別されている。
- JaUIの提供範囲を超える適合を無条件に保証する表現になっていない。
- 外部基準との差異または追加要求がある場合、その理由を説明できる。
- 適用するSC、対象機能、責務範囲、適用・非該当・例外の根拠と判断主体を追跡でき、未判定を非該当と扱っていない。
- 要求・下位仕様・実装・証拠への参照と主張の段階を追跡でき、検証済みと合格、Component単体のSC評価とページ全体の適合表明を混同していない。

ここではレビュー時の確認観点のみを示し、具体的なテスト方法や適合判定手順は定義しません。

### JAUI-A11Y-003: UIの意味・状態を支援技術へ公開する

本要求は、[JaUI Design Principles v0.1](./design-principles.md)の原則2「アクセシビリティを後付けしない。」、原則7「見た目より意味・セマンティクスを優先する。」を具体化する共通要求です。
Component / Pattern SpecificationおよびReference Implementationから、要求ID `JAUI-A11Y-003` で参照できます。

JAUI-A11Y-001はアクセシビリティを設計段階から扱い、下位仕様で明示することを扱い、JAUI-A11Y-002は外部基準を根拠としてJaUIの責務範囲へ具体化することを扱います。
JAUI-WEB-002がUIの目的・役割・期待される振る舞いに対応するセマンティクスの選択を扱うのに対し、本要求は利用者に必要な意味情報を支援技術へ公開することを扱います。
本要求は初期状態だけでなく、状態・値等の更新後も必要な意味情報を取得可能にすることを扱います。
JAUI-A11Y-013は、この意味情報の公開を前提として、入力前のラベル・指示の提供条件と可視ラベル・アクセシブルネームの整合を扱います。
JAUI-A11Y-007は、これを前提として、利用者が変化や処理結果を認識できる伝達方法とタイミングを扱います。
JAUI-A11Y-008は、エラー状態や説明と対象との関連付け等の意味情報の公開を前提として、エラーの特定・説明・修正支援を扱います。
JAUI-A11Y-009は色だけに依存しない視覚的な情報伝達を扱い、非色彩の手がかりがあることだけで本要求の意味情報の公開を満たすとはみなしません。
JAUI-A11Y-010はテキスト・UIのコントラストを扱い、視覚的な識別可能性を確保することだけで本要求の意味情報の公開を代替しません。

JAUI-A11Y-012は動き・アニメーション等の時間的・視覚的な負担と制御を扱います。動きの抑制や代替表現だけでは本要求を代替せず、抑制後も必要な意味・状態を支援技術から取得可能にします。

JaUIのComponent / Pattern SpecificationおよびReference Implementationは、利用者がUIを理解または操作するために必要な目的、役割、名前、状態、値その他の意味情報を、支援技術から取得可能な形で公開しなければならない。

これらの情報は、可能な場合は標準HTML要素その他のWeb標準が提供するネイティブなセマンティクスによって表現しなければならない。

ネイティブなセマンティクスだけでは必要な意味情報を表現できない場合は、関連するWAI-ARIA等の仕様・ガイダンスに基づいて補完しなければならない。

#### 外部基準との関係・対象範囲

本要求は、JAUI-A11Y-002に基づき、少なくとも以下の標準・ガイダンスを参照して具体化します。

- [WCAG 2.x Success Criterion 4.1.2 Name, Role, Valueの解説](https://www.w3.org/WAI/WCAG22/Understanding/name-role-value.html)
- [WAI-ARIA](https://www.w3.org/TR/wai-aria/)
- [WAI-ARIA Authoring Practices Guide (APG)](https://www.w3.org/WAI/ARIA/apg/)
- [HTML Standard](https://html.spec.whatwg.org/multipage/)および関連するWeb Platform仕様
- [デジタル庁デザインシステム（DADS）のアクセシビリティガイダンス](https://design.digital.go.jp/dads/guidance/accessibility/)

標準の要求とガイダンスの助言・例示を区別し、APGおよびWCAGの解説はガイダンスとして扱います。
本要求は必要な意味情報の公開を扱い、情報ごとに専用のARIA属性を要求するものではありません。
また、WCAG 4.1.2全体や利用先のWebコンテンツ全体への適合を保証するものではありません。

本要求では、個別ComponentのAccessible Name算出方法、個別のARIA role / state / propertyの割り当て、aria-label / aria-labelledby / aria-describedby等の利用ルール、Live Region、Screen Reader固有の読み上げ結果は定義しません。
色だけに依存しない視覚的な情報伝達の横断要求はJAUI-A11Y-009で扱います。
テキスト・UIのコントラストの横断要求はJAUI-A11Y-010で扱います。
動き・アニメーションへの配慮の横断要求はJAUI-A11Y-012で扱います。
キーボード操作、フォーカス管理・表示、Pointer / Touch Target、Motion / Animationの具体要件も定義しません。
これらは後続Issueまたは個別Component / Pattern Specificationで定義します。

#### 検証可能性

下位仕様またはReference Implementationのレビューでは、少なくとも以下を確認できることを目指します。

- Component / Patternの目的・役割が支援技術から判別可能である。
- 利用者が識別するために必要な名前が、支援技術から取得可能である。
- 操作や理解に必要な状態・値等が、必要に応じて支援技術から取得可能である。
- 標準HTML等が提供するネイティブなセマンティクスを不要に上書き・置換していない。
- ARIA等を使用する場合、その必要性と適用するrole / state / property等の根拠を説明できる。
- 視覚的表現だけに依存して意味・状態を伝えていない。

### JAUI-A11Y-004: キーボード操作可能性を確保する

W3C Understandingの解説に基づき、サイズの評価では、実際の操作可能領域内に水平・垂直の軸に沿った24×24 CSS pxの正方形が収まることを確認します。非矩形のターゲットでは、バウンディングボックスの幅・高さだけで十分とはみなしません。

| 例外 | 適用条件 |
|---|---|
| Spacing | 各小ターゲットのバウンディングボックスの中心に直径24 CSS pxの円を置いたとき、その円が別ターゲットや別の小ターゲットの円と交差しないように配置されている。 |
| Equivalent | 同じページ上の別の操作対象によって同じ機能を実現でき、その操作対象がSC 2.5.8を満たす。 |
| Inline | ターゲットが文章内にある、または非ターゲットのテキストの行高によってサイズが制約される。 |
| User Agent Control | ユーザーエージェントがターゲットのサイズを決定し、作成者がそのサイズを変更していない。 |
| Essential | ターゲットの特定の提示方法が伝達する情報に本質的である、またはその情報の提示に法的に要求される。 |

Spacingは、実際の操作可能領域とその位置関係に基づく円の判定として扱い、単純な「要素間に何pxの余白があればよい」という固定条件へ置き換えません。
小ターゲット同士の円だけでなく、円と別ターゲットの操作可能領域との関係も確認します。
文章外の操作対象をInlineと一律に扱うことや、標準HTML要素という理由だけでUser Agent Controlを適用することはしません。各例外の条件を対象ごとに説明します。
Inlineの行高は文字の流れに直交する方向として扱い、縦書きでは水平方向になります。
ターゲット内の位置によって値やカーソル位置を選択するスライダー、色選択領域、編集可能領域等は、SC 2.5.8の注記に従って一つのターゲットとして扱います。

SC 2.5.5の44×44 CSS pxはAAAの参考情報として扱い、AAの必須条件として導入しません。
これらの文書の全要求を一括して取り込むものではなく、本要求単独で各達成基準全体や利用先のWebコンテンツ全体への適合を保証するものではありません。
WCAGのバージョン・適合レベルに関する全体方針も、本要求では確定しません。

フォーム関連UIでは、入力欄、チェックボックス・ラジオボタンと操作可能なラベル、選択操作、エラー修正リンク・ボタン等を対象として検討します。

これらは適用を理解するための例であり、特定の寸法・配置・例外適用を確定するものではありません。エラーの特定・説明・修正支援はJAUI-A11Y-008に従います。

- JaUI、ユーザーエージェント、利用先の制御範囲と確認事項を区別し、標準要素の利用だけを理由として確認を省略していない。
- Theme・状態・カスタマイズ後も、既存の操作・フォーカス・コントラスト・ターゲット・情報提供の要求をそれぞれの条件で確認できる。
- 必要な要求、確認条件・方法、責務と再確認事項が、要求ID `JAUI-A11Y-014` を通じて下位仕様から追跡できる。

ここでは参照条件とレビュー時の確認観点を示し、具体的なテスト方法、環境別の検証手順や適合判定手順は定義しません。

### JAUI-A11Y-015: ポインター操作の代替・取消可能性を確保する

本要求は、[JaUI Design Principles v0.1](./design-principles.md)の原則1「Web標準を置き換えない。拡張する。」、原則2「アクセシビリティを後付けしない。」、原則3「「適合」より「検証可能性」を重視する。」、原則4「フレームワークに依存しない。」、原則8「カスタマイズ可能だが、壊しやすくしない。」を具体化する共通要求です。
Component / Pattern SpecificationおよびReference Implementationから、要求ID `JAUI-A11Y-015` で参照できます。

JAUI-WEB-001〜JAUI-WEB-003はWeb標準の利用、意味・セマンティクス、標準の状態・操作・イベント等の契約の維持を扱います。
本要求は、これらとJAUI-A11Y-001・JAUI-A11Y-002を前提として、JaUIが提供・制御するポインター操作の代替と、実行前の中止・実行後の取消・押下結果の復元の条件を扱います。
JAUI-A11Y-004のキーボード操作可能性と、本要求の単一ポインターによる代替操作は別の義務です。キーボード代替だけで単一ポインター代替を満たすとはみなしません。
JAUI-A11Y-011はターゲットサイズ・間隔を扱い、操作開始後の中止・取消やジェスチャー代替を代替しません。
JAUI-A11Y-013のラベル・指示とJAUI-A11Y-014の表示変更への耐性は、代替・中止・取消操作の理解と利用可能性について併せて確認し、それぞれの条件を再定義しません。

JaUIのComponent / Pattern SpecificationおよびReference Implementationは、JaUIが提供・制御する機能について、適用される基準の条件・例外に従い、複数点・経路依存ジェスチャーを要しない単一ポインター操作、およびドラッグを要しない単一ポインター操作を確保しなければならない。

単一ポインターで操作できる機能は、以下に示すSC 2.5.2の4条件の少なくとも1つを満たさなければならない。
すべての操作に解放時の実行やUndoを一律に要求してはならない。

各Component / Pattern Specificationでは、対象操作と状態、押下・移動・解放時の期待結果、適用する取消条件、必要な単一ポインター代替、例外・非該当の根拠、確認条件・方法、およびJaUIと利用先の責務を明示しなければならない。
ドラッグ・複数点・経路依存操作を提供しないComponent / Patternに、それらの操作の実装を要求するものではありません。その場合も、提供する単一ポインター操作へのSC 2.5.2の適用は別に確認します。

#### 外部基準との関係・対象範囲

本要求は、JAUI-A11Y-002に基づき、以下の標準・ガイダンスを参照して具体化します。

- [WCAG 2.2 Success Criterion 2.5.1 Pointer Gestures（A）](https://www.w3.org/TR/WCAG22/#pointer-gestures)
- [WCAG 2.2 Success Criterion 2.5.2 Pointer Cancellation（A）](https://www.w3.org/TR/WCAG22/#pointer-cancellation)
- [WCAG 2.2 Success Criterion 2.5.7 Dragging Movements（AA）](https://www.w3.org/TR/WCAG22/#dragging-movements)
- [W3C Understanding Pointer Gestures](https://www.w3.org/WAI/WCAG22/Understanding/pointer-gestures.html)
- [W3C Understanding Pointer Cancellation](https://www.w3.org/WAI/WCAG22/Understanding/pointer-cancellation.html)
- [W3C Understanding Dragging Movements](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html)
- [HTML Standard](https://html.spec.whatwg.org/multipage/)および関連するWeb Platform仕様

WCAGの規範的達成基準およびHTML Standardの要求と、Understanding・APG・DADSのガイダンスによる助言・例示を区別します。
3つの達成基準は、対象と条件・例外を分けて扱います。

| 基準 | 適用条件・例外 |
|---|---|
| SC 2.5.1 | 複数点・経路依存ジェスチャーを用いる機能は、経路依存ジェスチャーなしの単一ポインターでも操作可能にする。当該ジェスチャーが本質的な場合は例外とする。 |
| SC 2.5.2 | 単一ポインターで操作できる機能に、下記4条件の少なくとも1つを適用する。ジェスチャーやドラッグの有無だけで対象を限定しない。 |
| SC 2.5.7 | ドラッグを用いる機能は、ドラッグなしの単一ポインターでも達成可能にする。ドラッグが本質的な場合、または機能がユーザーエージェントによって決定され作成者が変更していない場合は例外とする。 |

3つの基準はWebコンテンツがポインター動作を解釈する操作を対象とし、ユーザーエージェント・支援技術自体を操作するために必要な動作には適用しません。
SC 2.5.1の経路依存ジェスチャーとSC 2.5.7のドラッグは同一ではなく、両方に該当する場合は両基準を確認します。代替操作にも適用されるSC 2.5.2等の要求を確認します。

SC 2.5.2の選択条件は以下のとおりです。

| 条件 | 充足条件 |
|---|---|
| No Down-Event | ポインターの押下（down-event）を、機能のいかなる部分の実行にも使用しない。 |
| Abort or Undo | 機能の完了は解放（up-event）時であり、完了前に中止する仕組み、または完了後に取り消す仕組みがある。 |
| Up Reversal | 解放によって、先行する押下の結果を元に戻す。 |
| Essential | 押下時に機能を完了することが本質的である。 |

これらは代替条件であり、すべてを同時に要求しません。Abort or Undoの中止と取消も選択肢です。
押下時に機能の一部として状態変更を開始する操作を、単に解放時に確定するという理由でNo Down-Eventに分類してはならない。その場合は他の充足条件を確認します。
押下・解放はプラットフォーム上の操作段階として扱い、特定のDOMイベント名や「mouseup時のみ実行」という契約をCoreで指定しません。
SC 2.5.2の注記では、キーボードまたはテンキーのキー押下を模倣する機能は本質的とされます。この注記を一般のフォーム選択・送信操作へ一律に拡張しません。

本質的であることの判断は、[WCAGのessentialの定義](https://www.w3.org/TR/WCAG22/#dfn-essential)に従います。
取り除くと情報・機能が根本的に変わり、適合する別の方法では情報・機能を実現できないことを、対象操作ごとに説明します。実装の容易さや既存実装の都合だけを例外の根拠にしません。
適用対象外とする場合、またはユーザーエージェント提供機能の例外を使う場合も、対象と制御主体、変更の有無を明示します。

#### フォーム関連UIと責務範囲・下位仕様への委譲

フォーム関連UIへの適用例として、下位仕様で以下を具体化します。

- Text Field：独自に提供する選択・クリア等の付加操作について、押下・移動・解放と完了・中止・取消時の値や選択状態を明示する。ユーザーエージェントが提供する標準テキスト選択との境界を区別する。
- Select：選択肢の選択・確定・閉じる操作を区別し、独自ポップアップでは押下・移動・解放時の候補・確定値と、適用する取消条件に応じた誤選択回避の期待結果を明示する。ネイティブ選択UIとJaUIが制御する操作を区別する。
- Checkbox / Radio：選択操作の完了タイミング、適用する中止・取消条件と期待状態を明示する。標準の選択・グループ状態遷移を維持し、HTML標準のactivation取消と利用者によるポインター操作の中止を混同しない。
- フォームPattern：JaUIが提供する送信・リセットのUI操作について、完了・中止・取消条件と利用先への引渡し範囲を明示する。並べ替え等のドラッグ操作を提供する場合は、同じ機能を達成するドラッグ不要の単一ポインター代替を具体化する。

標準HTML要素のネイティブな操作・状態遷移と、JaUIが追加・変更する独自操作やイベント処理を区別します。
標準要素を使っていることだけを理由に全操作を適用対象外とせず、JaUIによる拡張が標準契約や基準の充足を妨げていないことを確認します。
ネイティブな契約を維持することと、JaUI独自のポインター契約を満たすことは、それぞれの制御範囲に応じて確認します。

JaUI側は、提供・制御するUI操作の代替と適用する中止・取消・復元の仕組み、その利用条件・制約を扱います。JaUIが制御する範囲の責務はJaUIに残し、利用先へ転嫁しません。
利用先側は、追加イベントハンドラー、独自ジェスチャー、カスタマイズ後の操作、および送信・保存・削除等の業務処理とその結果を確認します。
UI操作を実行前に中止すること、UIの値・状態を取り消し・復元することと、送信済み・保存済み・削除済みの業務処理を取り消すことは区別します。
JaUIのUI操作の中止・取消機構だけを理由に利用先の業務処理も取り消せるとは保証せず、処理を引き渡す条件と両者の責務を下位仕様で明示します。

Component / Pattern Specificationでは、要求ID・SC、対象機能と制御主体、初期・操作中・完了後の状態、押下・移動・解放時の期待結果、適用する取消条件、単一ポインター代替、例外・非該当の根拠、確認条件・方法、利用先での再確認事項を追跡可能にします。
適用しない項目にも理由を明示します。Reference Implementationでは契約を満たす実装と、ネイティブ操作・独自操作の境界を示します。
正式な記録形式、試験ID・結果の接続方法、適合判定の全体方針は後続のTesting / Conformanceへ委ねます。

これらの文書の全要求を一括して取り込むものではなく、本要求単独で各達成基準全体や利用先のWebコンテンツ全体への適合を保証するものではありません。WCAGのバージョン・適合レベルに関する全体方針も、本要求では確定しません。
個別ComponentのDOM構造、イベント名、イベントAPI、CSS、Lit実装、具体的なキー割当、実行時テストコード、環境別の詳細な試験手順は本要求では定義せず、下位仕様へ委ねます。

### JAUI-A11Y-016: 操作の予測可能性を確保する

本要求は、[JaUI Design Principles v0.1](./design-principles.md)の原則1「Web標準を置き換えない。拡張する。」、原則2「アクセシビリティを後付けしない。」、原則3「「適合」より「検証可能性」を重視する。」、原則4「フレームワークに依存しない。」、原則5「日本のWeb利用を第一級のユースケースとして扱う。」を具体化する共通要求です。
Component / Pattern SpecificationおよびReference Implementationから、要求ID `JAUI-A11Y-016` で参照できます。

本要求は、JaUIが提供・制御するUIについて、フォーカス取得・設定変更による文脈変化と、文字キーショートカットの有効条件を扱います。
JAUI-WEB-003は標準の状態・操作・イベント等の契約維持、JAUI-A11Y-004はキーボードからの利用可能性・離脱・終了、JAUI-A11Y-005はフォーカス順序・移動・維持・復帰、JAUI-A11Y-007は状態変化・結果の伝達、JAUI-A11Y-013は入力前のラベル・指示の提示・関連付けを扱い、これらを併せて適用します。
本要求はそれらの責務を再定義せず、操作を契機とする変化の発生条件を明確にします。

JaUIのComponent / Pattern SpecificationおよびReference Implementationは、コンポーネントがフォーカスを受けることだけで、文脈変化を開始してはならない。

UIコンポーネントの値・選択・チェック等の設定変更によって、自動的に文脈変化を起こしてはならない。ただし、利用者がそのコンポーネントを利用する前に、その挙動を説明されている場合は許容する。
状態変化・処理結果の事後通知だけを、利用前の説明の代替としてはならない。

印字可能文字のみで構成されたキーボードショートカットを提供する場合は、無効化可能、非印字キーを含む再割当可能、または対象コンポーネントにフォーカスがあるときのみ有効、の少なくとも一つを満たさなければならない。
ショートカットの実装自体や、三つの条件すべてを満たすことは要求しない。

各Component / Pattern Specificationでは、操作の契機と期待結果、文脈変化の有無と判断根拠、適用条件、必要な事前説明の提供主体・タイミング・対象との関連付け、ショートカットの採用条件、検証観点およびJaUIと利用先の責務を明示しなければならない。

#### 外部基準との関係・対象範囲

本要求は、JAUI-A11Y-002に基づき、以下の規範本文を優先して具体化します。

- [WCAG 2.2 Success Criterion 3.2.1 On Focus（A）](https://www.w3.org/TR/WCAG22/#on-focus)
- [WCAG 2.2 Success Criterion 3.2.2 On Input（A）](https://www.w3.org/TR/WCAG22/#on-input)
- [WCAG 2.2 Success Criterion 2.1.4 Character Key Shortcuts（A）](https://www.w3.org/TR/WCAG22/#character-key-shortcuts)
- [WCAGの文脈変化（changes of context）の定義](https://www.w3.org/TR/WCAG22/#dfn-changes-of-context)

WCAGの規範的達成基準・定義と、Understanding、APG、DADSの解説・ガイダンスによる助言・例示を区別します。ガイダンスを規範本文の条件・例外に置き換えません。

| 基準 | 適用条件・例外 |
|---|---|
| SC 3.2.1 | コンポーネントがフォーカスを受けることを契機に、文脈変化を開始しない。事前説明による例外はない。フォーカス移動一般や、リンク・ボタン等の明示的な起動操作による遷移・フォーカス管理を一律に禁止する条件ではない。 |
| SC 3.2.2 | コンポーネントの設定変更によって文脈変化が自動的に起きる場合に適用する。対象の利用前にその挙動を説明している場合に限り許容する。設定変更と、送信ボタン・リンク等の明示的な起動操作を区別する。 |
| SC 2.1.4 | 大文字・小文字、数字、句読点、記号等の印字可能文字のみを用いるショートカットに適用する。単一文字に限定せず、複数文字で構成するものも対象とする。無効化する仕組み、Ctrl / Alt等の非印字キーを一つ以上含むよう再割当する仕組み、またはそのショートカットの対象コンポーネントにフォーカスがある間だけ有効にすることの、少なくとも一つを満たす。 |

文脈変化は、ページ全体を同時に見られない利用者が、気付かずに起きると混乱し得る大きな変化として、WCAGの定義に従って判断します。
ユーザーエージェント、ビューポート、フォーカス、ページの意味を変える内容の変化を含みます。別ウィンドウの表示、別ページへの遷移、別コンポーネントへのフォーカス移動、ページ内容の大きな再配置等が例です。
通常の値・チェック状態の更新、処理結果の表示、補助情報・メニューの展開等は、それだけで文脈変化とは判定しません。フォーカスやページの意味等にもたらす実際の影響を確認します。
例えば、フォーカス取得時の補助情報表示と、その取得による別画面への遷移を区別します。設定変更に伴う通知を適切に伝達しても、必要な事前説明を省略できません。
明示的な起動操作による文脈変化や、それに伴うJAUI-A11Y-005のフォーカス管理は、その起動操作とフォーカス取得・設定変更を分けて評価します。

SC 2.1.4のフォーカス限定条件は、ページ上のどこかにフォーカスがあることではなく、そのショートカットの対象コンポーネントにフォーカスがあることを意味します。
下位仕様では通常の文字入力、IMEの変換・確定操作、音声入力との衝突を検討し、ショートカットが誤作動しない条件と検証観点を明示します。具体的なキー割当やイベント処理方法は本要求で確定しません。

#### フォーム関連UIの適用例・責務境界

次の例は下位仕様で契約を具体化する観点であり、特定のUI・APIの実装を要求するものではありません。

| 対象 | 下位仕様で具体化する事項 |
|---|---|
| Text Field | フォーカス取得だけで送信・遷移しない。文字入力とIME変換・確定がショートカットを誤作動させない条件を定める。 |
| Select | フォーカス取得時の自動遷移と、選択変更による自動的な文脈変化を分ける。後者には利用前の説明を必要とする。ネイティブUIの操作とJaUIが追加する動作を区別する。 |
| Checkbox / Radio | チェック・選択の通常の状態更新と、別画面への遷移や別対象へのフォーカス移動等を区別する。設定変更で後者が自動的に起きる場合は事前説明条件を適用する。 |
| フォームPattern | 入力変更による自動送信が文脈変化を起こすかを確認する。別画面への遷移、フォーカス管理、項目別・フォーム共通の事前説明の位置・関連付け・提供主体を明示する。 |

Coreは共通の適用条件・例外と既存要求との境界を定義します。Component / Patternは、フォーカス取得、設定変更、明示的な起動、ショートカットそれぞれの状態・契機・期待結果・事前説明の契約を具体化します。
Reference Implementationは、JaUIが提供・制御する動作について、その下位契約を満たします。JaUIが提供する動作に必要な説明の内容・提示条件・関連付けを下位仕様で定義し、JaUIが制御する表示・動作について責務を利用先へ転嫁しません。
利用先は、追加ハンドラー、ルーティング、自動送信、独自ショートカット、フォーム全体の事前説明と、組み合わせ・カスタマイズ後の最終検証を担当します。
利用先が追加する自動的な文脈変化については、利用先が挙動を説明し、対象の利用前に提示・関連付けされることを確認します。JaUIの提示手段を利用する場合も、追加した挙動の内容・適用条件の責務を明確にします。
下位仕様では、JaUIが提供する動作と利用先が追加する動作を分け、説明内容の提供主体と提示・関連付けの担当主体、利用前に把握できるタイミング・位置、JaUIが検証できる範囲と利用先での再確認事項を追跡できるようにします。

操作契約から将来の試験へ、少なくとも次の情報を要求ID `JAUI-A11Y-016` とともに追跡できるようにします。

| 記録項目 | 内容 |
|---|---|
| 対象・事前状態・契機 | フォーカス取得／設定変更／明示的起動／ショートカットを区別し、ネイティブ操作と独自動作、制御主体を示す。 |
| 期待結果・適用条件 | 状態更新、文脈変化の有無・根拠、フォーカスへの影響、該当SCと関連Core ID、非該当の理由を示す。 |
| 説明・ショートカット | 事前説明の要否、内容・提供主体・提示タイミング・関連付け、採用するショートカット代替条件と有効範囲を示す。 |
| 検証先 | 下位仕様の確認項目から、将来の試験条件・期待結果・結果への参照を示す。IME・音声入力等の競合確認を含める。 |

正式な記録形式、試験ID・結果の接続方法、適合判定の全体方針は後続のTesting / Conformanceへ委ねます。
本要求単独で各達成基準全体や利用先のWebコンテンツ全体への適合を保証するものではありません。WCAGのバージョン・適合レベルに関する全体方針も、本要求では確定しません。
個別ComponentのDOM、イベント名・API、Lit実装、具体的なキー割当、実行時テストコード、環境別の詳細試験手順は本要求では定義しません。

#### 検証可能性

下位仕様またはReference Implementationのレビューでは、少なくとも以下を確認できることを目指します。

- フォーカス取得だけで文脈変化を開始せず、事前説明による例外を設けていない。
- 設定変更と明示的な起動操作が区別され、自動的な文脈変化がある場合は対象の利用前にその挙動を説明する条件を確認できる。
- 文脈変化の有無を実際の影響に基づいて説明でき、通常の状態変化・フィードバックと混同していない。事後通知を事前説明の代替としていない。
- 印字可能文字のみのショートカットについて、単一文字・複数文字を含めて適用を判断でき、採用する代替条件と有効範囲を説明できる。ショートカットの提供や三条件すべてを一律に要求していない。
- 通常の文字入力、IME変換・確定、音声入力との競合・誤作動を下位仕様の検証観点として追跡できる。
- フォーム関連UIの状態・契機・期待結果、事前説明の提供主体・タイミング・関連付けと責務が明示されている。
- JaUIの提供・制御する動作と利用先の追加動作を区別し、JaUIの責務を転嫁せず、カスタマイズ後の再確認事項を示している。
- 既存要求と重複・矛盾せず、要求ID `JAUI-A11Y-016` から下位契約と将来の試験条件・期待結果を追跡できる。

ここではレビュー時の確認観点を示し、具体的なテスト方法、環境別の検証手順や適合判定手順は定義しません。

## 13. Testing

### 13.1 評価原則と文書責務

本章は、[14章 Conformance](#14-conformance)の方針と[14.6 Testingへの引渡し](#146-testingへの引渡し)を、共通の追跡情報・評価の判定規則へ具体化します。既存の個別要求の意味・適用条件・例外を再定義しません。
評価はWeb Standardsを基盤とし、Litその他のフレームワークに依存する規則にしてはならない。

Coreは共通原則、最小追跡情報、方法の適用範囲と限界、環境選定、証拠・再評価、Conformanceへの接続を担います。Component / Pattern Specificationは対象機能・状態・操作・利用条件と責務の契約を具体化します。
個別テストケース、具体的な実行手順・試験方法、記録フォーマット、試験IDの採番形式、ツール選定・自動化・運用の詳細は下位のTest Specification / Resultsへ委譲します。本章はこれらの作成や実行の完了を意味しません。

### 13.2 追跡モデルと最小情報

Core要求 → Component / Pattern Specification → Reference Implementation → Test Specification → Test Results → Conformance評価について、要求から対象・結果へ、結果から対象実装・試験・下位契約・根拠となる要求へ双方向に追跡可能にしなければならない。
WCAG SCは要求・下位契約との対応として接続します。Decision Recordsは判断根拠として参照し、要求本文や試験証拠の代替にはしません。

| 論理情報 | 最小内容 |
|---|---|
| 要求・外部基準 | Core要求ID、WCAG参照版、SC番号・Level・規範参照、対応理由。AAA参考基準・JaUI独自品質要求を区別する。 |
| 対象・下位契約 | Component / Pattern、機能・状態・操作・利用条件、下位仕様の文書IDまたは識別可能な参照・節・リビジョン。 |
| 責務・適用判断 | JaUI／ユーザーエージェント／利用先の制御範囲と担当主体、適用条件・例外、判断理由・判断主体。 |
| 実装 | 対象実装への参照・リビジョン、設定・組み合わせ。未実装の場合は不存在を明示する。 |
| 試験仕様 | 識別可能な試験参照、対象契約、方法、前提・入力・操作条件、期待結果、評価環境への参照。 |
| 結果・証拠 | 試験・実装への参照、実施状態、実際の結果、判定・理由、日付・評価主体、証拠、不具合・例外・制約・残余リスク。 |
| 評価の要約 | 対象範囲、参照結果、評価済み・未評価条件、主張の段階、現在の対象への結果の有効性・再評価要否。 |

1要求対複数SC、1 SC対複数要求、1試験対複数契約を許容し、一対一対応を強制してはならない。SCとの対応がない独自要求も区別して記録します。
共通する試験・証拠は共有できますが、要求・SC・条件ごとの期待結果と判定を追跡できなければならない。一つの観点の合格を他の観点の合格に置き換えません。

双方向追跡は相互参照または対応表で実現でき、リンクの二重記載は必須ではありません。識別子・参照は対象を一意に識別でき、結果を引用する際も参照先と版を維持できなければならない。文書・試験・実装・証拠が未作成の場合は未作成と明示し、架空の参照や結果で埋めません。
これらは情報の意味の最小要件であり、データスキーマ、ファイル配置、採番形式を固定するものではありません。

### 13.3 適用・実装・評価の判定軸

[14.4 SCの適用判定と状態の区別](#144-scの適用判定と状態の区別)に従い、以下を独立した情報として記録しなければならない。

| 軸 | 値・扱い |
|---|---|
| 適用判断 | 適用／非該当／未判定。対象範囲・条件と判断理由・主体を示す。 |
| 規範例外 | 適用判断と別に、例外の有無・確認状態、SCの規範根拠、成立条件・証拠、例外以外に残る義務を示す。 |
| 実装段階 | 未実装／一部実装／実装済み。対象リビジョンと実装範囲を限定する。 |
| 評価実施状態 | 未実施／一部実施／実施済み。実施した対象・条件・方法と未実施部分を示す。 |
| 評価結果 | 合格／不合格／判定保留。未実施の場合は結果なしとする。 |
| 変更後の扱い | 過去結果を保持し、現在の対象への有効性、再評価要否・対象・理由を別に示す。 |

非該当は、限定した対象範囲にSCの適用条件を満たす機能・内容がないことを根拠とします。予定機能の未実装、未検証、JaUIの責務外を非該当の代替理由にしてはならない。ユーザーエージェント提供UIも一律に非該当とせず、SC固有の例外とJaUIによる変更を確認します。
適用条件や例外の成立を確認できない場合は未判定・未確認として残し、例外適用や合格として扱いません。非該当・例外適用の判断も根拠を追跡し、条件変更時の影響分析の対象にします。

合格は、限定した対象の適用される要求・条件を満たすと証拠に基づいて判断した結果、不合格は満たさないと確認した結果です。証拠不足や判断未確定は判定保留とし、理由・不足情報・対応主体を記録します。
実施済み・検証済みは合格を意味しません。静的レビューを実施していても、実行時評価を実施済みと扱ってはならない。
部分的な合格を未評価の状態・操作・環境へ拡張してはならない。要約でも不合格・保留・未評価を残し、全体を合格と表現して隠しません。

### 13.4 試験方法の適用範囲と限界

下位試験仕様は、対象要求・契約に応じて評価方法を選び、自動化する観点と人が判断する観点、選定理由と限界を明示しなければならない。

| 方法 | 主な対象 | 限界 |
|---|---|---|
| 静的レビュー | 仕様、セマンティクス、責務、適用条件・例外、文言。 | 実際の動作・表示・読み上げを保証しない。 |
| 機械的検査 | 構造・属性、計測可能な条件、DOM・アクセシビリティ情報。 | 検出可能な範囲に限定され、意味や文言の適切さ、全操作・プロセスを保証しない。 |
| ブラウザ操作 | 状態遷移、イベント、設定・組み合わせでの挙動。 | 模擬入力や特定環境の成功を実機・全環境へ一般化できない。 |
| キーボード評価 | 到達・操作・離脱、順序、フォーカス、ショートカット。 | キーイベントの成功だけでは操作体験・支援技術連携を保証しない。 |
| 視覚確認・計測 | 拡大、リフロー、間隔、配色、コントラスト、遮蔽、操作領域。 | 画像だけでは操作可能性や意味情報の公開を保証しない。 |
| 支援技術評価 | 名前・役割・状態、説明、通知、読み順、操作。 | 評価したOS・ブラウザ・支援技術の組み合わせに限定される。 |

複数方法を必要に応じて組み合わせ、機械的検査の成功だけで人による判断を要する事項を合格としてはならない。DOMやアクセシビリティツリーの検査と、実際の支援技術による評価を区別します。
特定ツール（axe-core、Playwright等）をCoreの必須実装技術に固定しません。下位試験で採用する場合は、方法・版・検査範囲を記録し、ツールの判定と要求・SCの評価結果を区別します。

### 13.5 評価環境の選定と記録

評価環境は対象要求・利用条件・リスクに応じて選定しなければならない。すべての組み合わせを常時必須とはしませんが、選定理由、評価対象範囲、未評価条件と理由、残余リスクを明示します。将来の[10章 Interoperability](#10-interoperability)の対応環境方針と整合させます。

再現と判定に必要な情報を、少なくとも以下の観点から記録します。

- OS・版、ブラウザ・版、支援技術・版、使用ツール・版。
- 実装・Core・下位仕様のリビジョン、利用先設定・組み合わせ・試験データ。
- Viewport、表示方向、文字拡大・Zoom、リフロー、テキスト間隔、配色・Theme・Tokens、背景・隣接色。
- 入力方式（キーボード、ポインター、タッチ、IME等）、関連する設定・版、操作前提。

使用しない項目はその旨を示し、不明・未評価と区別します。選定した環境での合格を未評価環境の合格へ拡張しません。
Viewport変更と実際のZoom、合成イベントと実IME・実機操作を区別し、代替・模擬手段で確認した範囲と確認できない範囲を記録します。
環境を選定することは、ページ全体のSCや適合要件を省略する理由にはなりません。

### 13.6 証拠・再現性と再評価

結果は期待結果・実際の結果・判定理由、試験日・評価主体、再現条件、証拠参照（ログ、スクリーンショット、手動観察等）、不具合・例外、未評価事項・残余リスクを記録しなければならない。
証拠を対象試験・仕様・実装リビジョン・環境に結び付け、証拠未作成や未実施理由を明示します。手動観察も観察条件と内容を残し、第三者が結果と根拠を確認できるようにします。

仕様・実装・環境等の変更時は、関連要求・SC・下位契約・試験・結果への影響分析を行い、再評価の要否と対象を決定しなければならない。

| 変更契機 | 主な影響分析・再評価先 |
|---|---|
| Core、参照基準、Component / Pattern Specification | 対応付け、適用条件・例外、期待結果、既存判定。 |
| Reference Implementation、DOM、イベント、フォーカス処理 | 意味情報、操作、状態遷移、通知、統合動作。 |
| Theme・Tokens、利用先CSS・背景・配置 | コントラスト、非色彩の手がかり、拡大、リフロー、ターゲット、遮蔽。 |
| ブラウザ・OS・支援技術・IME | ネイティブUI、意味情報の公開、入力・読み上げの相互運用。 |
| コンテンツ・設定・組み合わせ・業務処理 | 適用条件、ラベル・説明、エラー、ページ・完全なプロセス。 |

分析結果には変更内容、影響する範囲、再実施する試験・条件、実施しない範囲と理由、判断主体、残余リスクを残します。影響なしと判断した範囲にも根拠を示します。
すべての試験の無条件な再実行は要求しません。ただし、過去の合格を無条件に現在の合格として継承してはならない。再評価が必要な条件の過去結果は現在の対象の合格根拠とせず、未再評価であることを示します。
再実施は過去の結果・証拠を上書きせず、変更前後の対象と結果の関係を追跡可能にします。

## 14. Conformance

本章は、[JAUI-A11Y-002](#jaui-a11y-002-標準的なアクセシビリティ基準を参照する)に基づき、アクセシビリティの目標、評価・適合表明の単位と段階、適用判定、責務境界を定義します。既存の個別要求の意味・適用条件を再定義しません。

### 14.1 目標・参照版と規範の区別

JaUIは、[WCAG 2.2、2024-12-12 Recommendation](https://www.w3.org/TR/2024/REC-WCAG22-20241212/)のLevel AおよびAA達成基準（Success Criteria、SC）をアクセシビリティの目標とします。
AAの目標にはAも含みます。個々のSCへの対応と、Webページの適合に必要な[適合要件（Conformance Requirements）](https://www.w3.org/TR/2024/REC-WCAG22-20241212/#conformance-reqs)の充足を区別しなければならない。
AAAの参考基準やJaUI独自の品質要求は、A・AAの目標と区別して説明します。

[WCAGの規範／参考の区別](https://www.w3.org/TR/2024/REC-WCAG22-20241212/#interpreting-normative-requirements)に従い、SC、規範的定義、適合要件を根拠とします。Understanding WCAG、APG、DADSのガイダンス、WCAGの注記・例示は助言・解釈のための参考情報として区別します。

将来のWCAG版、同一版の改訂・正誤表は、要求・適用条件・既存評価への影響をレビューし、採用する参照版と変更理由をCoreの変更として記録します。参照先の更新だけで目標を自動変更したり、既存結果を新しい基準での検証済み・適合確認済みへ転用したりしてはならない。

### 14.2 評価と適合の単位

WCAG適合の単位はWebページ全体です。ページの一部を除外して適合を判定することはできません。ページが一連のプロセスに属する場合は、完全なプロセスの全ページが対象レベル以上で適合する必要があります。
[WCAG 2.2の適合要件](https://www.w3.org/TR/2024/REC-WCAG22-20241212/#conformance-reqs)の五つの要件をすべて扱います。

| 適合要件 | 評価で区別する事項 |
|---|---|
| 適合レベル | AAではすべてのA・AAのSCを満たすか、規範の条件を満たすAA適合代替版を提供する。 |
| ページ全体 | 全体を対象とし、画面サイズに応じて自動提示される表示の変種も含める。 |
| 完全なプロセス | 活動を完了する一連の全ページを対象とし、一部の部品・ステップの合格で代替しない。 |
| アクセシビリティサポーテッドな技術利用 | SCの充足に依存する技術の使用方法が支援技術・ユーザーエージェントでサポートされることを確認する。サポートされない方法で提供する情報・機能も、サポートされる方法で利用可能にする。技術名だけで判定しない。 |
| 非干渉 | 適合達成に依存しない技術が有効・無効・未サポートでもページが適合要件を満たし、他の内容へのアクセスを妨げない。SC 1.4.2、2.1.2、2.2.2、2.3.1は依存しない内容も含む全コンテンツについて扱う。 |

JaUI独自のComponent品質評価と、WCAGに基づく正式な適合表明を区別しなければならない。
Component / Pattern単体やライブラリについては、JaUI要求への評価結果や、限定した対象機能・条件で確認したSCの評価結果を報告できます。ただし、それをWebページ全体のWCAG 2.2 AA適合表明へ置き換えたり、単体の無条件の適合を宣言したりしてはならない。
Reference Implementationの例示ページも、そのページ全体と属する完全なプロセスを評価した範囲に限って適合を判断できます。
ライブラリの合格、自動評価ツールの合格、JaUIの採用だけを理由として、利用先サイトの適合を保証してはならない。JaUIの責務外という理由で、利用先ページの評価から内容を除外してはならない。

### 14.3 主張の段階と正式な適合表明

要求定義、設計、実装、検証、ページ・プロセスの適合確認を独立した段階として区別しなければならない。前段階の完了を理由に、後段階の完了を自動的に主張してはならない。

| 段階 | 主張できる内容・必要な根拠 |
|---|---|
| 要求を定義済み | 対象要求IDと仕様本文が存在する。設計・実装・検証の完了を意味しない。 |
| 設計上対応 | 対象の下位仕様が、要求・適用条件への対応を説明している。実装結果とは区別する。 |
| 実装済み | 対象実装・リビジョンが存在する。動作検証や品質要求の充足を意味しない。 |
| 検証済み | 対象・条件・環境・証拠・結果を伴う検証を実施した。検証済みは合格を意味せず、合否判定を別に明示する。 |
| 特定のページ・プロセスで適合を確認 | 対象範囲についてA・AAのSCとすべての適合要件を確認している。対象外のページ・プロセスへ拡張しない。 |

検証の実施だけで品質要求を満たしたと表明してはならない。未検証の対象について適合を宣言してはならず、証拠・環境・対象・制約を伴わない適合宣言を避けなければならない。
現時点のCore要求定義は、Componentの実装・実行時検証・WCAG 2.2 AA適合確認の完了を意味しません。

[WCAGの正式な適合主張は任意](https://www.w3.org/TR/2024/REC-WCAG22-20241212/#conformance-claims)です。正式に主張する場合は、以下のWCAG必須項目を記録しなければならない。

- 主張日。
- ガイドライン名、版、URI（Web Content Accessibility Guidelines 2.2、[https://www.w3.org/TR/WCAG22/](https://www.w3.org/TR/WCAG22/)）。
- 達成した適合レベル。
- 対象ページの簡潔な記述。URIの一覧または範囲を表す記述を用い、サブドメインの包含範囲も示す。
- 適合達成に依存するWebコンテンツ技術の一覧。

JaUIの表現方針では、これらのWCAG必須項目に加え、対象リビジョン、評価日・評価主体、証拠参照、確認環境、利用条件・制約、対象となる完全なプロセスも追跡可能にしなければならない。追加項目をWCAG自体の必須項目と混同しません。

### 14.4 SCの適用判定と状態の区別

SCごとに対象機能、適用条件・規範的例外、JaUIが制御する範囲、ユーザーエージェントが提供する範囲、利用先が担う範囲を区別しなければならない。
適用判断、実装状態、検証の実施状態、合否判定は別の情報として扱います。

| 区分 | 意味・判断の根拠 |
|---|---|
| 適用 | 対象機能・内容がSCの適用条件を満たす。評価対象と条件を明示する。 |
| 非該当 | 限定した対象範囲に、SCの適用条件を満たす機能・内容が存在しない。対象範囲と理由を記録する。 |
| 例外適用 | SCの規範的例外に該当する。根拠・成立条件を確認し、非該当と一括にしない。例外以外に残る義務も扱う。 |
| 未判定 | 適用判断に必要な情報が不足している。非該当へ置き換えない。 |
| 未実装 | 対象の予定機能が実装されていない。将来の要求が非該当である理由にはしない。 |
| 未検証 | 対象・条件について評価証拠がない。合格・不合格へ置き換えない。 |
| 検証済み | 検証を実施し、証拠・結果を示せる。合否判定とは独立する。 |
| 合格／不合格 | 対象の適用される要求・条件を満たす／満たさないと証拠に基づいて判断した。Componentの合格をページの適合と扱わない。 |

Component / Patternの仕様策定主体は、JaUIの提供範囲について適用条件・例外・責務と理由を整理します。実装の評価主体は実際の対象・条件と証拠を確認し、利用先の評価主体は最終ページ・完全なプロセスについて再判定します。判断主体を記録しなければならない。
ユーザーエージェント提供UIは一律に非該当とせず、各SCの例外条件とJaUIが追加・制御する動作を区別します。
機能追加、設定・スタイル・構造・動作の改変、Componentの組み合わせ、ユーザーエージェント・支援技術等の環境変更で成立条件が変わる場合は再評価しなければならない。JaUIでの非該当判定を利用先や将来の提供範囲へ自動的に転用しません。

### 14.5 仕様体系と利用先の責務境界

既存の仕様体系とDecision Recordsによる判断根拠を維持し、Core → Component / Pattern → Reference Implementation → Test Specification / Results → 利用先のページ・完全なプロセス評価へ接続します。

| 主体・文書 | 担当する範囲 |
|---|---|
| Core | 共通目標、適用・表現方針、責務境界を定義する。 |
| Component / Pattern Specification | 対象機能・状態・利用条件、適用SC・例外、既存要求への対応、JaUIと利用先の契約を具体化する。 |
| Reference Implementation | JaUIが提供・制御する範囲で下位契約を満たす。対象リビジョンを示す。 |
| Test Specification / Results | 要求・下位契約から、評価条件・証拠・結果を追跡可能にする。 |
| 利用先の評価主体 | 固有のコンテンツ・業務処理、組み合わせ、追加ハンドラー、設定・スタイル等の改変を含む最終ページ・完全なプロセスを評価する。 |

JaUIは提供・制御する動作と利用条件を明確にし、その範囲の不備や必要な検証を利用先へ転嫁してはならない。
利用先は組み込み後の条件を確認し、変更で影響を受けるSCと適合要件を再評価します。ライブラリの評価証拠は利用先の評価に参照できますが、最終ページ・完全なプロセスの適合保証には転用しません。

### 14.6 Testingへの引渡し

下位仕様・実装・評価へ、少なくとも次の情報を追跡可能にしなければならない。これらは情報の意味の最小要件であり、具体的なデータスキーマや記録フォーマットではありません。

| 情報 | 最小内容 |
|---|---|
| 要求 | Core要求ID、関連するComponent / Pattern Specificationへの参照。 |
| 外部基準 | WCAG参照版、SC番号・Level・規範参照。SCとの対応がないJaUI独自要求も区別する。 |
| 対象・責務 | 対象機能・利用条件、JaUI／ユーザーエージェント／利用先の制御範囲と担当主体。 |
| 適用判断 | 適用・非該当・未判定、例外の有無・成立条件、判断理由・判断主体。 |
| 状態 | 要求・設計・実装の段階、検証実施状態と合否判定を別々に示す。未実装・未検証・不合格を区別する。 |
| 証拠参照 | 対象リビジョン、評価条件・環境・日付・評価主体・結果・制約への参照。証拠未作成も明示する。 |

共通の追跡・判定、試験方法の範囲と限界、環境選定・証拠・再評価の規則は[13章 Testing](#13-testing)に従います。個別ケース・具体的実行手順・試験方法・記録フォーマット・採番形式・ツール選定は下位のTest Specification / Resultsへ委譲します。既存個別要求の追跡観点を置き換えず、それらと接続します。
[WCAG 2.2 AAギャップ分析](../reviews/accessibility-wcag22-aa-gap-analysis.md)は調査時点の記録として保持します。[Issue #48](https://github.com/sumile-lab/JaUI/issues/48)と[Issue #50](https://github.com/sumile-lab/JaUI/issues/50)による14章・13章の規則整備でGAP-009のP1仕様設計対応を完了することは、Componentの実装・実行時検証やWCAG 2.2 AA適合確認の完了を意味しません。
