# Accessibility Core要求とWCAG 2.2 AAのギャップ分析

## 1. 結論・調査範囲

**A11Y-001〜012をもってAccessibility全体の網羅を宣言することはできない。** 意味・状態の公開、キーボード、フォーカス、エラー、色、コントラスト、ターゲットサイズ、動きには横断要求がある。一方、入力前のラベル・指示と可視ラベルを含む名前、拡大・リフロー・間隔変更への耐性、単一ポインターでの代替・取消、予測可能な操作、検証結果への追跡には不足がある。サイトの内容・プロセス・ページ集合に関する達成基準は、12要求を増やすだけでは保証できない。

本書は分析・判定・後続Issue候補であり、要求本文やComponentの詳細仕様を追加しない。表の「本文で明示」はJaUIの責務に関する仕様上の判定であり、SC全体の充足や実装検証済みを意味しない。

## 2. 照合方法と判定の読み方

SCの適用条件・例外とCoreの要求本文、対象範囲、検証可能性を照合した。リンクがあるだけでは充足としない。A11Y-001の設計原則とA11Y-002の外部基準参照は全行の背景にあるが、具体的な未定義要求の代わりには数えない。逆方向にも全15要求を確認した（4章）。

| 責務区分 | 判定の意味 |
|---|---|
| 既存横断要求 | 本文が該当する責務を扱う。下位仕様化と試験は依然必要 |
| Component・Pattern | 個別の構造・操作・利用条件で具体化すべき。Core追加を直ちに必要としない |
| 利用先 | 文言・コンテンツ、業務、ページ・プロセスや部品の組み合わせをアプリケーションが決定・検証 |
| 通常非該当 | フォーム優先の提供範囲に該当機能がない。利用先にも非該当、または将来も不要という意味ではない |
| 要追加検討 | 複数部品に共通する制約に不足があり、Core追加・修正の判断が必要。提案は5章で示す |

責務が重なる行は複数区分を併記する。「本文で明示／一部／関連参照のみ／記述なし」はSCと要求本文の関係で、責務区分や実装結果とは独立する。「関連参照のみ」は一般的な標準契約またはリンクがあるが該当の具体義務は未定義、という意味。「記述なし」は当該義務が未定義で、一般原則も存在しないという意味ではない。

各対応要求IDはCoreの該当要求本文へリンクする。検証先は**予定の下位仕様・試験条件**であり、結果への既存リンクではない。実際の条件・期待結果・環境・証跡の管理は6章へ申し送る。

### 根拠資料の扱い

各行のSCリンクは版を固定した規範文への根拠である。[WCAGの規範／参考の区別](https://www.w3.org/TR/2024/REC-WCAG22-20241212/#interpreting-normative-requirements)に従い、用語定義を含む規範本文と注記・例示を分ける。表は主要条件の要約であり、全例外の最終判定はリンク先の定義と提供機能に照らして下位仕様で記録する。

補助資料は次の判断に使用する。HTML・ARIAの仕様と助言を区別し、APG・DADSをWCAGの適合条件として一括採用しない。

| 資料 | 種別・分析への利用 |
|---|---|
| [HTML：label](https://html.spec.whatwg.org/multipage/forms.html#the-label-element)、[fieldset](https://html.spec.whatwg.org/multipage/form-elements.html#the-fieldset-element) | 規範仕様。ラベルの関連付け・選択グループの構造をネイティブの意味と操作で具体化できる根拠（GAP-001・010） |
| [HTML：autofill](https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#autofill)、[入力目的一覧](https://www.w3.org/TR/2024/REC-WCAG22-20241212/#input-purposes) | 規範仕様。入力目的は単なるAccessible Nameや入力形式とは異なる（GAP-004） |
| [WAI-ARIA 1.2](https://www.w3.org/TR/wai-aria-1.2/)、[Accessible Name and Description Computation 1.2](https://www.w3.org/TR/accname-1.2/) | ARIAは規範仕様、AccName 1.2は調査時点のWorking Draftとして成熟度を区別。名前・説明・状態の取得方法は下位仕様で採用版を決める（GAP-001・010） |
| [APG：キーボードインターフェース](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/) | ガイダンス。Tab順、複合部品内の移動、フォーカスと選択の区別を検討する補助（GAP-006・010）。パターンを選べば適合済みとはしない |
| [DADS：アクセシビリティ](https://design.digital.go.jp/dads/guidance/accessibility/) | ガイダンス。外観構造・操作・コントラストと利用先コンテンツの責務境界をレビューする補助。DADSの具体値・実装をJaUIの要求に転記しない |

[JAUI-A11Y-008][A008]で関連参照された3.3.2を入力前支援まで対応済みにすること、[JAUI-A11Y-004][A004]のキーボード代替を2.5.1/2.5.7の単一ポインター代替として使うこと、[JAUI-A11Y-012][A012]の動き低減を時間制限や音声制御の充足とすることは、責務の隙間を隠す。これらは既存要求の矛盾ではなく、対象範囲の違いである。

AAAの2.2.5（再認証後のデータ保持）、2.2.6（タイムアウト）、2.3.3（操作起因の動き）、2.4.12/2.4.13（強化された遮蔽・面積）、2.5.5（44×44）、3.3.5/3.3.6/3.3.9（支援・全入力の予防・認証強化）はAAの必須条件に含めない。日本語IME中のEnter、全角・半角・ふりがな等の入力支援、平易な日本語、再認証後の復帰は日本向け品質として検討できるが、それぞれを独立したAAのSCがあるかのように扱わない。

## 5. ギャップ一覧と後続Issue候補

**P1は後続のCore・Theme・フォームコンポーネント設計へ進む前に解消すべきギャップ**とする。共通契約・評価の基盤が未定義で、後から直すと複数部品・既定スタイル・責務分担を作り直す項目を選ぶ。P1の「解消」は必要な仕様上の判断・要求と委譲先を合意して記録することであり、未実装部品の実機試験完了ではない。Issue候補を置くだけでは解消しない。

| Design Principles | 原則2・3・5・7・8・10に基づく判断。SC・手順を複製せず、検証可能性・日本向けフォーム・意味優先の判断根拠にする |

| Component / Pattern Specification | 構造、名前・説明・状態、操作、既定表示・組み合わせ条件、利用先が渡す内容と再確認事項。各SCの適用/例外とCore IDを明示 |
| Decision Records | ネイティブで足りるか、独自化する理由、代替案、標準との差異・例外の証拠。説明可能性を記録し、要求や試験結果の代わりにはしない |
| Reference Implementation | 下位仕様の契約を実装。Lit固有APIはここで決め、仕様上の選択と実装の制限を区別 |
| Test Specification / Results | 条件・期待結果・手順・環境・実測・証跡・合否・未実施理由。実装と同じリビジョンの下位仕様/Core IDへ接続 |

現在はCoreの「確認できることを目指す」レビュー観点と要求ID参照まで追跡可能で、**下位仕様→実行条件→結果の鎖はまだ存在しない**。結果ありと未検証を混ぜず、対象外は機能の不存在や例外の根拠を記録して扱う。未実施は対象外にしない。

Testing / Conformanceに、次の共通記録を提案する（形式・ツール・JSON Schemaは確定しない）。

- Core ID、SC番号・版・Level、下位仕様の節とリビジョン、試験ID、実装リビジョンを相互参照する。複数要求に共通する試験は1つの結果から参照し、別の観点の合否を残す。
- テーマ・状態・背景/隣接色・表示方向・Viewport・Zoom・テキスト間隔・入力手段・データ・操作前提を記録する。例外は名称だけでなく条件と証拠を残す。
- 自動チェック、DOM/アクセシビリティ情報、目視・キーボード/ポインター、支援技術による確認を区別する。自動判定できない文言の適切さ・読み順・全プロセスの結果を未検証のまま合格にしない。
- 結果は期待結果・実際の結果、OS/ブラウザー/支援技術と版、実施日、証跡、判定者、未実施理由を持つ。対応環境の範囲は将来のInteroperabilityと整合させる。
- 利用先の追加CSS・背景・文言・配置・イベント・Theme値が変わるときの再確認項目を明示する。既定条件の合格を任意のカスタマイズへ拡大しない。

## 7. 不確実性・次フェーズへの条件

分析は現行本文とフォーム優先の代表例からの推奨判断であり、将来のAPI・Theme・提供するPatternの確定結果ではない。通常非該当の再判定、日本語・縦書き・混在文での間隔例外、独自Selectの操作モデル、ブラウザー・支援技術の相互運用、対象外/不可欠性の最終判断は下位仕様の機能・条件が決まった時点で必要になる。AccName等の採用版もその時に確定する。

**現状のままAccessibilityを完了扱いにしてTheme / Design Tokensの具体設計へ進むことは推奨しない。** 次の条件を満たせば、残るP2・P3を追跡しながら次領域へ進める。

1. GAP-001・002・003・006で共通契約と責務境界を決定し、必要なCore追加/修正を別Issueで完了する。既存要求の具体化で足りる判断なら理由と委譲先を記録する。
2. GAP-009でWCAG 2.2 AA目標、適合表現の範囲、追跡と評価条件の記録規則を確定する。[JAUI-A11Y-010][A010]・011・012の既定条件と、表示変更耐性の条件をTheme側が参照できるようにする。
3. P2は各フォームComponent/Patternの仕様・実装完了前の必要課題として対応先と依存を記録する。P3は採用機能・ガイド整備を着手条件として管理する。実Issueの作成・採番は本作業では行わない。
4. 下位仕様・試験結果を得た時点で本表を更新する運用を定め、未検証事項を合格へ置換しない。#6は保留を維持し、本分析の前提依存にしない。

### 本分析の完了確認と未実施の動作確認

完了判定はSC番号・名称・Levelの規範本文との照合（A31/AA24、重複・欠落なし）、15要求との本文照合、責務と条件付き非該当の理由、フォームへの影響・優先度・Issue粒度・依存関係、Markdownとリンクの整合、変更が本ファイルのみであることとする。実装のWCAG適合認証はこの判定に含めない。

リポジトリには操作対象のUI・開発サーバー・Component試験がまだなく、本Issueは分析だけなので実装のブラウザー操作試験は未実施。外部資料の規範本文の照合とJaUIの動作検証は区別する。

実機・別OS・Screen Reader・日本語IME・利用者のパスワード管理・利用先のセッション/保存処理は未実施である。人が後続実装時に行う手順は次のとおり。

1. 下位仕様・実装・試験のリビジョンと、OS・ブラウザー・支援技術・IME等の版を記録し、6章のケースを試験IDに接続する。
2. 実機の日本語入力で変換・確定・修正を行い、Select/Checkbox/Radioの選択と離脱、送信後のエラー把握・修正・再送信を確認する。Screen Readerで名前・説明・更新後の状態・必要な通知とフォーカス継続を確認し、実際の結果を残す。
3. 実ブラウザーの文字拡大・Zoom・間隔上書き・縦横表示とタッチ操作を確認する。Viewport変更だけで実際のZoomや実機タッチを確認済みにはしない。長い日本語ラベル・エラー、テーマ変更、実操作領域、非遮蔽を評価する。
4. 利用先の本人情報入力と認証で目的指定・補完・貼り付け・パスワード管理を試し、複数ステップでの再入力、期限延長、該当取引の確認・訂正を全プロセスで確認する。コンテンツ・業務側の判定とJaUIが提供する機構を分けて結果を記録する。
